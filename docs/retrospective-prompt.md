# 기능 구현 회고 작성용 프롬프트

아래 내용을 복사한 뒤 기능 이름과 검토 범위를 채운다.

> EKL의 **[기능 이름]** 구현 회고를 작성해 줘. 검토 범위는 **[커밋·브랜치·작업 폴더]**야. 독자는 이 프로젝트를 처음 보는 백엔드·프론트엔드·AI 개발자야.
>
> 1. `docs/development-history.md`에서 해당 기능의 개발 내역과 아키텍처를 찾고, 파트별 개발 프롬프트·설계서의 요구사항을 실제 변경 코드·테스트와 대조해 줘. 출처는 문서 경로, 코드 경로 또는 커밋 ID를 넣어 줘.
> 2. 해결하려던 업무 문제와 요구사항, 선택한 구현과 이유, 트랜잭션·권한·데이터 경계 중 이 기능에서 중요한 항목을 설명해 줘. 당시 검토 기록이 있는 대안과 실제로 관찰한 장애만 다뤄 줘.
> 3. 사용자 동작에서 저장 또는 응답까지 이어지는 흐름을 Mermaid 그림으로 표현해 줘. 외부 인터페이스, 저장소, 비동기 작업, 더미 응답의 위치가 해당되면 표시해 줘. 기존 아키텍처 이미지를 인용할 때는 현재 구현과 설계상 예정된 구성을 구분해 줘.
> 4. 시험 명령과 확인한 결과, 모의 응답 또는 시험 데이터로 검증한 범위, 미검증 항목을 정리해 줘. 기록에 없는 수치와 테스트 결과는 추정하지 말고 확인되지 않았다고 표시해 줘.
> 5. 실제 작업에서 드러난 교훈과 후속 과제를 작성해 줘. 공개 회고에는 합성 예제만 사용하고 내부 기획서 본문, 접속 정보, 원문·개인정보는 포함하지 말아 줘.

회고 구성을 **업무 문제 → 구현 결정 → 아키텍처 → 검증 → 다음 작업** 순서로 유지한다.

## 기능별로 추가할 질문

| 기능 | 프롬프트에 추가할 질문 |
|---|---|
| Core 기반 | 프레임워크와 업무 패키지를 어떻게 나눴고, Service AOP가 트랜잭션과 호출 로그에 각각 어떻게 적용되는가? |
| 문서·폴더 | 등록 전에 상속 권한을 어떻게 미리 보고, 등록·버전 추가·게시·폐기를 어떻게 구분하는가? |
| Web 공통과 문서함 | 프로토타입이 공통 컴포넌트로 어떻게 옮겨졌고, 서버 상태와 작업 탭 상태를 어디에서 관리하는가? |
| VOC·Case | VOC 원문과 정제문을 어떻게 다루며, Case에서 사람의 결정과 종결 결과를 어떻게 기록하는가? |
| 지식·배포 | 지식 초안과 배포 요청의 현재 구현 경계는 어디이고, 최종 승인부터 수신함 생성까지 어떤 연결이 필요한가? |
| 문서 파싱·LLM 호출 | 등록 응답 이후 작업자가 어떻게 파싱하고 재시도하며, 실제 파싱과 더미 생성은 어떤 인터페이스를 공유하는가? |
